I. MARCO CONCEPTUAL
1.1 ¿Qué es un patrón de diseño?
Un patrón de diseño es una solución probada a un problema de diseño que se repite, descrita de forma que pueda
reutilizarse en contextos distintos. Gamma, Helm, Johnson y Vlissides (el "Gang of Four", GoF, 1994) catalogaron 23
patrones orientados a objetos y describieron cada uno con cuatro elementos: nombre, problema, solución y
consecuencias. Las consecuencias importan tanto como la solución: todo patrón agrega clases e indirección, y solo
se justifica si resuelve un problema real.
Los patrones existen en distintos niveles. En el Laboratorio 04 se trabajaron patrones arquitectónicos (capas,
monolito modular, eventos), que organizan el sistema completo. En este laboratorio se trabajan patrones de diseño,
que organizan las clases dentro de un módulo, como los diseñados con UML en el Laboratorio 05.
Figura 1. Catálogo GoF de 23 patrones. Se marcan los siete que se implementan en esta guía. Gráfico elaborado con Python (matplotlib).

1.4 Olores de código y refactorización hacia patrones
Un olor de código (Fowler, 2018) es una señal superficial de un problema de diseño: métodos largos, condicionales
que crecen con cada requisito, código duplicado o clases que conocen demasiado. Kerievsky (2004) propone
refactorizar hacia patrones: no se diseña "con patrones" desde el inicio, sino que se introduce un patrón cuando un
olor concreto lo pide, en pasos pequeños y protegidos por pruebas.
Para medir el efecto se usa la complejidad ciclomática (McCabe, 1976): el número de caminos independientes de un
método. La herramienta radon la calcula para Python y la clasifica de A (1–5, simple) a F (41 o más). Un método con
complejidad mayor a 10 es difícil de probar y de modificar.
Bash — medir antes y después
pip install radon pytest
radon cc -s -a src/ # complejidad ciclomática por método y promedio
radon raw -s src/ # líneas de código (SLOC)
radon mi -s src/ # índice de mantenibilidad

1.6 Flujo de trabajo y riesgos de usar IA para diseñar
Figura 2. Refactorización hacia patrones asistida por IA. Diagrama generado con Graphviz (DOT).
Los asistentes de IA conocen muy bien el catálogo GoF, y ese es justamente su riesgo. Errores típicos que se deben
vigilar:
▪ "Patternitis" (sobreingeniería): propone Abstract Factory para dos clases o un Visitor donde basta una función.
Si el patrón no elimina un olor concreto, se rechaza.
▪ Singleton por defecto: lo sugiere para fábricas o configuraciones; introduce estado global y dificulta las pruebas.
Es preferible inyectar la dependencia.
▪ Cambios de comportamiento silenciosos: al refactorizar puede alterar una regla (por ejemplo, reintentar también
los pagos rechazados). Solo las pruebas lo revelan.

class ConReintentos(PasarelaPago):
def __init__(self, interna: PasarelaPago, intentos: int = 3):
self._interna, self._intentos = interna, intentos
def cobrar(self, monto, celular):
for _ in range(self._intentos):
try:
return self._interna.cobrar(monto, celular)
except TimeoutError:
continue
return ResultadoPago(False)

class FabricaPasarelas:

def crear(self, medio: str) -> PasarelaPago:
if medio not in self._creadores:
raise ValueError(f"Medio de pago no soportado: {medio}")
return ConReintentos(self._creadores[medio]())

def completar(self, prompt):
if prompt not in self._cache:
self._cache[prompt] = self._interno.completar(prompt)
return self._cache[prompt]
# ---------- CHAIN OF RESPONSIBILITY: guardrails de salida ----------
class Guardrail(ABC):
def __init__(self, siguiente=None):
self._siguiente = siguiente
def validar(self, texto: str) -> str:
texto = self._aplicar(texto)
return self._siguiente.validar(texto) if self._siguiente else texto
@abstractmethod
def _aplicar(self, texto: str) -> str: ...
class SinPrecios(Guardrail):
def _aplicar(self, texto):
if "S/" in texto:
raise ValueError("Guardrail: la IA incluyó un precio")
return texto
class SinAfirmacionesProhibidas(Guardrail):
PROHIBIDAS = ["orgánico certificado", "cura", "garantizado"]
def _aplicar(self, texto):
for palabra in self.PROHIBIDAS:
if palabra in texto.lower():
raise ValueError(f"Guardrail: afirmación no permitida '{palabra}'")
return texto

# ADR-005: Patrones de diseño en el módulo Pedidos
- **Estado:** Aceptado (21/10/2026)
## Contexto
confirmar_y_pagar() tenía complejidad 15; cada medio de pago o proveedor de IA nuevo obligaba
a modificar el servicio. La salida del LLM no es confiable (puede inventar precios).
## Decisión
Adapter + Strategy + Factory para pagos; Decorator para reintentos y caché; State para el ciclo
de vida (Lab 05); Observer para notificaciones; Chain of Responsibility para guardrails de IA.
Se rechazan Singleton y Abstract Factory (ver bitácora, entrada 1).
